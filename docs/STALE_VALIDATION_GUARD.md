## Implemented boundary

Validation reserves the single-process context from its persisted queued record through execution and context persistence. A readable package check happens before validation. After successful validation, schema version 1 and its fingerprint are persisted before the validation becomes claimable; this captures generated Salesforce bundles and `.forceignore` rather than invalidating a legitimate build.

A deployment request first replays any existing claim, including failed/interrupted runs and replay after mutation or restart. For a first claim, Dispatch checks the saved context against current inputs and persists the queued deployment and claim together before starting work. It rechecks immediately before the executor. Queued and running deployments retain the same lease through terminal status. One validation claims only one deployment; intentional retries require fresh validation.

Package assembly and plan/strategy writes persist invalidation before starting work, including partially failing operations, and reserve the context across long operations. Validation and first claims cannot enter that interval. Returning inputs from A to B to A does not restore an invalidated validation, including after restart.

Selected connection writes pass through the same boundary: Box add/select/delete, Salesforce REST/add/select/delete, OAuth callback saves, provider checks, Salesforce open/recovery and delayed scratch-org selection. New OAuth and scratch workflows are rejected while a context is active. A workflow already started can finish its remote operation, but its local selected-target save is rejected if a run has acquired the lease. A created scratch org's ID/identity and recovery guidance remain visible if its selection cannot be saved.

Production `shellstate` updates also participate. Box token rotation and Salesforce lifecycle refresh/invalidation update only their original record, preserve the current selection, and reject conflicting stale tokens. HTTP read/modify/save requests carry a process-local baseline: unchanged fields preserve concurrent refreshes, and conflicting writes or a changed destination fail. Callers receive actionable conflict guidance. The browser handles a stale-validation response by discarding the old apply action, loading the current plan and returning to review; failed plan loading uses the existing retry flow before fresh validation.

Missing/unsupported context versions and unreadable inputs fail closed. Unreadable/corrupt run history is preserved and blocks new work or context mutation; repair storage and restart Dispatch. A failed initial validation/claim save starts no executor. A failed terminal validation-context save leaves it unclaimable. Interrupted work is restored as failed and never executes automatically.

## Fingerprint coverage and limits

The fingerprint covers plan/package identity, provider inclusion, strategy, file paths, permissions and contents, including runtime configuration, resolved create-new IDs, generated outputs, `.forceignore`, package build environment files and `.dispatch/package.json`. It includes nonsecret selected Box/Salesforce record, account/org/principal/client/endpoint bindings including effective nonsecret client-ID fallbacks, and Box's `BOX_PARENT_FOLDER_ID`, `BOX_WORKSPACE_NAME` and `BOX_ALLOW_ROOT_FOLDER` overrides. Tokens, secrets and readiness/display timestamps in connection state are excluded; only opaque digests and version/invalidation flags are added to run history. Package bytes are read for hashing, never copied into that history.

Both selected provider bindings are conservatively included, even when one provider is excluded from a plan. `.git`, `node_modules`, `dispatch/audit` and other root `.dispatch` operator-state files are excluded; deployable generated outputs are included. Symlinks, unsupported file types, unavailable inputs, observed changes during a file read and packages exceeding 1 GiB fail closed. Large packages can hold the context mutex while their fingerprint is read.

The contract is one local Dispatch process/primary API handler, not shared cross-process coordination. External editors, independent processes, runtime environment changes and remote provider state remain outside its lease. Fingerprinting detects observed drift at its read boundaries; it does not make inputs immutable between those reads, bind every remote provider observation, undo already-applied operations or prevent remote provisioning started before the lease. Exact immutable execution snapshots are separate architecture scope.
